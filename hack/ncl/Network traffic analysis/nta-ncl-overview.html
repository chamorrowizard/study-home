DNS Traffic EASY

> Domain Name System (DNS) & Zone Transfers

Extract DNS record queries, parse full zone transfer payloads (AXFR over TCP port 53), extract subdomains, TTL metadata, and IP mappings.

// When to Use This Technique

  • Identify queried domains, record types (A, AAAA, MX, TXT, AXFR), or DNS tunneling indicators.
  • Analyze bulk DNS record dumps resulting from full domain zone transfers over TCP stream.
  • Extract IP addresses matching specific hostnames (e.g., "welcome" subdomain).

// Why This Specific Approach Works

Standard UDP DNS requests carry single queries. However, zone transfers (AXFR) use TCP (port 53) to reliably send the entire domain zone database in one or more response packets containing multiple answer records with uniform Time-To-Live (TTL) values.

// Key Commands & Display Filters

// Filter for DNS queries or specific query types in Wireshark:
dns.qry.type == 252 || dns.flags.response == 1
// Extract requested domain, record types, answer counts, and TTLs via tshark:
tshark -r DNS.pcap -Y "dns" -T fields -e dns.qry.name -e dns.qry.type -e dns.count.answers -e dns.resp.ttl
GOTCHA / PITFALL

Do not confuse IP Packet Time-To-Live (ip.ttl) with the DNS Record Time-To-Live (dns.resp.ttl). In CTF questions asking for "DNS TTL", extract the field directly from the DNS answer structure payload.

FTP & Credentials EASY

> FTP Protocol & Data Channel Carving

Recover cleartext credentials (USER / PASS), inspect server response codes, and isolate passive/active data transfers (ftp-data).

// When to Use This Technique

  • Extract plaintext login credentials sent over unencrypted FTP (TCP port 21).
  • Find authenticated sessions using response code 230.
  • Inspect file transfers (RETR / STOR) and directory listings (LIST) on secondary data channels.

// Why This Specific Approach Works

FTP separates control commands (port 21) from data transfers (dynamic or port 20). Following TCP streams on command traffic exposes plaintext commands, while filtering for protocol ftp-data exposes raw directory listings and downloaded binary/text files.

// Key Commands & Display Filters

// Isolate successful logins and credentials in Wireshark:
ftp.response.code == 230 || ftp.request.command == "USER" || ftp.request.command == "PASS"
// Extract FTP credentials and file transfer data via tshark:
tshark -r FTP.pcap -Y "ftp.request.command in {\"USER\",\"PASS\",\"RETR\"}" -T fields -e ftp.request.command -e ftp.request.arg
GOTCHA / PITFALL

Multiple packet bursts occurring within milliseconds in the capture represent split fragments of a single FTP response. Always follow the full TCP stream (Follow > TCP Stream) rather than reading isolated individual packets.

Telnet Streams EASY

> Telnet Session Replay & Interactive Streams

Reconstruct interactive remote terminal sessions over TCP port 23, separate server echo characters from client user input, and identify executed shell commands.

// When to Use This Technique

  • Reconstructing legacy system administrator interactions and credential inputs.
  • Extracting post-authentication commands executed during an interactive shell session.

// Why This Specific Approach Works

Telnet lacks transport encryption and transmits keyboard input key-by-key or line-by-line. Reassembling the TCP stream combines bidirectional flow, revealing both prompt text and user command input.

// Key Commands & Reassembly Filters

// Filter for Telnet traffic in Wireshark:
telnet || tcp.port == 23
// Reconstruct full interactive stream text via tshark:
tshark -r Telnet.pcap -q -z follow,tcp,ascii,0
GOTCHA / PITFALL

Telnet standard servers echo back typed characters (except passwords). In TCP stream views, duplicated characters represent the echoed response. Ignore duplicate echo characters, trailing punctuation, and periods that are part of prompt formatting.

802.11 / Wi-Fi MEDIUM

> 802.11 WEP / WPA Password Cracking & Decryption

Crack WEP initialization vectors (IVs) or WPA 4-way handshakes using aircrack-ng and wordlists like RockYou, then configure Wireshark to decrypt captured wireless frames.

// When to Use This Technique

  • Identify target Access Point BSSID via 802.11 Beacon Frames.
  • Crack legacy WEP keys (40-bit/104-bit) or perform WPA/WPA2 dictionary attacks against captured EAPOL handshakes.
  • Decrypt payload packets to inspect internal HTTP / administrative traffic.

// Why This Specific Approach Works

WEP uses weak RC4 encryption susceptible to statistical key derivation from initialization vectors (wlan.wep.iv). WPA/WPA2 derives encryption keys from the PSK and 4-way handshake parameters, allowing offline passphrase cracking.

// Key Commands & Decryption Setup

// Crack WPA/WPA2 capture against RockYou wordlist for target BSSID:
aircrack-ng -w /usr/share/wordlists/rockyou.txt -b C0:4A:00:80:76:E4 PCAP3.cap
// Wireshark Decryption Configuration Steps:
1. Edit → Preferences → Protocols → IEEE 802.11 2. Check [x] "Enable decryption" 3. Decryption Keys → Edit → Key type: wpa-pwd → Key: "passphrase:SSID"
GOTCHA / PITFALL

WEP key length calculation: A 64-bit WEP key uses a 40-bit secret key + 24-bit IV. A 128-bit WEP key uses a 104-bit secret key (13 hex/ASCII bytes) + 24-bit IV. Do not count the 24-bit IV when asked for user password input size.

TLS / Decryption MEDIUM

> HTTPS / TLS Traffic Decryption via SSLKEYLOGFILE

Decrypt encrypted HTTPS payload packets using external session key logs (sslkeylog.log) containing client pre-master secrets.

// When to Use This Technique

  • Analyzing encrypted HTTPS/TLS packet captures accompanied by an SSL key log file.
  • Extracting hidden flags, POST parameters, or HTTP response headers from TLS streams.

// Why This Specific Approach Works

Modern TLS (e.g., TLS 1.3 or Diffie-Hellman cipher suites) uses Perfect Forward Secrecy (PFS). Private RSA keys cannot decrypt PFS traffic, requiring client-generated key logs (CLIENT_RANDOM) to derive the session keys.

// Key Commands & Wireshark Settings

// Wireshark Decryption Setup:
1. Edit → Preferences → Protocols → TLS (or SSL) 2. (Pre)-Master-Secret log filename → Browse → Select sslkeylog.log
// Decrypt TLS and extract HTTP payload via CLI tshark:
tshark -r "SSL Decrypt.pcapng" -o "tls.keylog_file:sslkeylog.log" -Y "http" -T fields -e http.file_data
GOTCHA / PITFALL

Once keys are loaded, decrypted plaintext appears in a new tab at the bottom of the Packet Details pane or via Follow > TLS Stream. Standard http filters will not trigger until the key log file is correctly assigned.

IPv4 Dissection EASY

> IPv4 Binary Header Bitfield Dissection

Parse raw binary IPv4 headers, calculate field byte offsets (0-indexed), and extract Time-To-Live (TTL), protocol types, and Header Checksums.

// When to Use This Technique

  • Answering low-level packet structure questions from raw binary/hex matrices.
  • Extracting TTL (Offset Byte 8), Protocol ID (Offset Byte 9), or Header Checksum (Offset Bytes 10-11).

// Why This Specific Approach Works

An IPv4 header uses a standard 20-byte base format (assuming IHL=5). Byte offsets start strictly at 0: Byte 8 contains TTL (8 bits / 1 byte), and Bytes 10-11 contain the 16-bit Header Checksum.

// Offsets & CyberChef Workflows

// CyberChef Binary to Decimal/Hex Conversions:
Byte 8 (TTL): Copy 8-bit binary string → CyberChef Recipe: "From Binary" → Read Decimal value Bytes 10-11 (Checksum): Copy 16 bits → CyberChef Recipe: "From Binary" + "To Hex"
// Python script for rapid header offset extraction:
python3 -c 'b=bytes.fromhex("4500003ca99a400040064f93c0a880809fcb609a"); print(f"TTL:{b[8]} Proto:{b[9]} Checksum:{hex(b[10]*256+b[11])}")'
GOTCHA / PITFALL

Always count byte offset from 0 (0, 1, 2, 3...). The 9th byte in natural counting is Offset 8 (TTL). Ensure CyberChef treats input explicitly as "From Binary" rather than UTF-8 string text.

CAN Bus Automotive HARD

> CAN Bus Packet Payload Telemetry Decoding

Analyze Controller Area Network (CAN Bus) dumps, filter arbitration IDs, and apply C-code bitwise algorithms to calculate vehicle speed telemetry.

// When to Use This Technique

  • Decoding raw vehicle telemetry captures containing CAN IDs (e.g., Arbitration ID 589 / 0x24D).
  • Translating proprietary application payload bytes into physical units using provided C-code logic.

// Why This Specific Approach Works

CAN Bus provides standard frame transport without high-level application data schemas. Telemetry requires combining payload bytes via bit-shifts (e.g., data[3] << 8 + data[4]) and converting units (e.g., dividing by 100 and multiplying by 0.6213751 for MPH).

// Conversion Algorithm & Commands

// C Telemetry Formula Logic:
double raw = (frame.data[3] << 8) + frame.data[4]; double speed_mph = (raw / 100.0) * 0.6213751;
// Extract CAN frame payload bytes for CAN ID 589 (0x24d) via tshark:
tshark -r Candump.pcap -Y "can.id == 589 || can.id == 0x24d" -T fields -e can.payload
GOTCHA / PITFALL

Ensure Wireshark/tshark CAN IDs are checked in both decimal (589) and hexadecimal (0x24d) representations. Left shifting by 8 (<< 8) is equivalent to multiplying the high byte by 256.

Custom Protocols HARD

> Custom Binary Protocol Reassembly (Pandora)

Filter noise (SSH/HTTP), parse custom binary headers in Network Byte Order (Big-Endian), and decode magic integrity checks, request counts, and payload byte lengths.

// When to Use This Technique

  • Analyzing unknown binary C2 protocols operating over non-standard TCP ports.
  • Parsing structured binary headers: 4-byte count, 2-byte magic check, 4-byte length, followed by raw variable-length payload bytes.

// Why This Specific Approach Works

Applying negation filters (!(tcp.port == 22)) isolates proprietary TCP streams. Viewing the hex dump reveals binary integers encoded in network byte order (Big-Endian).

// Key Commands & Hex Filtering

// Isolate custom TCP stream by filtering background noise in Wireshark:
tcp && !(tcp.port == 22) && !(tcp.port == 80)
// Dump raw stream hex payload via tshark for manual field carving:
tshark -r pandora.pcap -Y "tcp && !(tcp.port == 22) && !(tcp.port == 80)" -x
GOTCHA / PITFALL

Remember to convert byte lengths from Hexadecimal to Decimal! For example, a length header byte sequence of 0x00 0x00 0x00 0x58 equals 88 decimal bytes of payload data.

HTTP & Files EASY

> HTTP Traffic Analysis & File Object Carving

Extract client User-Agent details, analyze web server response banners, correlate client/server IPv4 endpoints, and export transferred file objects to calculate payload MD5 checksums.

// When to Use This Technique

  • Identify client-side download tools (e.g., curl, wget) via the http.user_agent header.
  • Identify web server software (e.g., Apache, nginx) via the http.server header.
  • Carve downloaded files (images, binaries) from HTTP responses and derive MD5 hashes via CyberChef or Linux CLI.

// Why This Specific Approach Works

Unencrypted HTTP (TCP port 80) exposes headers in cleartext. Filtering by http.request shows client intent, while http.response establishes server details. The source IP of a response packet represents the server, and the destination IP represents the requesting client.

// Key Commands & Display Filters

// Isolate client requests and extract User-Agent strings via tshark:
tshark -r HTTP.pcap -Y "http.request" -T fields -e ip.src -e http.user_agent -e http.request.full_uri
// Extract server banners and response codes via tshark:
tshark -r HTTP.pcap -Y "http.response" -T fields -e ip.src -e http.server -e http.response.code
// Carve exported HTTP objects to disk and calculate MD5 hash:
tshark -r HTTP.pcap --export-objects "http,./extracted" && md5sum ./extracted/*
GOTCHA / PITFALL

When carving raw hex data from Wireshark or CloudShark into CyberChef, ensure you copy from the signature header (e.g., PNG signature 89 50 4E 47) down to the trailer (49 45 4E 44 AE 42 60 82) and apply the From Hex recipe before hashing.

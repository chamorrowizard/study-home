// src/lib.rs
//! Core Banking Engine Domain Logic
//! Demonstrates explicit public boundaries, invariant protection, and submodules.

pub mod account;

pub use account::{BankAccount, Currency};

/// Transaction Processor managing ledger state safely.
pub struct LedgerProcessor {
    total_processed: u64,
}

impl LedgerProcessor {
    pub fn new() -> Self {
        Self { total_processed: 0 }
    }

    /// Process a deposit cleanly with error propagation
    pub fn process_deposit(&mut self, account: &mut BankAccount, amount: f64) -> Result {
        account.deposit(amount)?;
        self.total_processed += 1;
        Ok(account.balance())
    }

    pub fn total_transactions(&self) -> u64 {
        self.total_processed
    }
}
// src/main.rs
//! Entry Point (Binary Target)
//! Consumes `lib.rs` strictly via the public crate interface (`playground::*`)

use playground::{BankAccount, Currency, LedgerProcessor};

fn main() -> Result<(), Box> {
    println!("--- Initializing Banking Core ---");

    let mut account = BankAccount::new("Alice", 250.00, Currency::USD);
    let mut processor = LedgerProcessor::new();

    // Invoking public interface method
    let new_balance = processor.process_deposit(&mut account, 150.50)?;

    println!("Owner: {}", account.owner());
    println!("Updated Balance: ${:.2}", new_balance);
    println!("System Total Ops: {}", processor.total_transactions());

    // UNCOMMENTING THIS WILL CAUSE A COMPILE ERROR:
    // account.balance = 999999.0; // Error: field `balance` of `BankAccount` is private!

    Ok(())
}
// src/account.rs
//! Submodule handling explicit Domain Invariants & Visibility Modifiers

#[derive(Debug, Clone, PartialEq)]
pub enum Currency {
    USD,
    EUR,
    GBP,
}

#[derive(Debug)]
pub struct BankAccount {
    owner: String,      // Private: enforces constructor usage & protects invariants
    balance: f64,        // Private: prevents illegal external mutation
    pub currency: Currency, // Public field
}

impl BankAccount {
    /// Public Constructor: External code MUST use this (struct literals are blocked)
    pub fn new(owner: &str, initial_balance: f64, currency: Currency) -> Self {
        Self {
            owner: owner.to_string(),
            balance: initial_balance.max(0.0), // Guard against invalid initial state
            currency,
        }
    }

    pub fn owner(&self) -> &str {
        &self.owner
    }

    pub fn balance(&self) -> f64 {
        self.balance
    }

    pub fn deposit(&mut self, amount: f64) -> Result<(), String> {
        if amount <= 0.0 {
            return Err("Deposit amount must be strictly positive".to_string());
        }
        self.balance += amount;
        Ok(())
    }

    /// Restricted Visibility: Visible anywhere inside this crate (e.g., in lib.rs),
    /// but COMPLETELY hidden from external users importing this crate!
    pub(crate) fn audit_log(&self) {
        println!("[AUDIT] Account owner: {}, balance: {}", self.owner, self.balance);
    }
}

Core Computer Science & Systems Essentials

Invariants & Encapsulation

Keeping fields private in lib.rs isn't just about clean code—it guarantees state consistency. In high-concurrency systems, unrestricted field access creates data race hazards and memory corruption.

CS Concept: Class-Level Invariants & Encapsulation Boundaries

Target Isolation (lib vs bin)

Cargo compiles lib.rs and main.rs into separate build artifacts. main.rs links against the compiled library crate just like any external dependency.

CS Concept: Linkage, Compilations Units & Dynamic/Static Binding

Black-Box Integration Testing

Unit tests inside lib.rs can access internal private fields. Integration tests in the top-level tests/ folder can only interact with public functions, testing real public contract guarantees.

CS Concept: Black-Box Verification & API Contracts

Zero-Cost Abstractions

Rust's module system is purely a compile-time concept. Enforcing pub and module access paths adds zero runtime performance cost while enabling aggressive compiler optimization (LTO).

CS Concept: Zero-Cost Abstractions & Link-Time Optimization

Fine-Grained Visibility (pub(crate))

Visibility isn't just binary. Using pub(crate) or pub(super) allows submodules to share internal engine methods without leaking them into your public API surface.

CS Concept: Principle of Least Privilege & Restricted Scope

API Facade (pub use Re-exporting)

Using pub use account::BankAccount; inside lib.rs flattens deeply nested internal folder structures into a clean, flat public API for external consumers.

CS Concept: Structural Design Patterns (Facade Pattern)

System Evolution: From Local Module to Distributed Architecture

01
Single Monolith

Single Binary with Module Separation

Code sits in one repository. Modules (lib.rs, account.rs) act as logical boundaries. Memory is shared in-process, and calls are direct zero-overhead function calls.

02
Cargo Workspace

Multi-Crate Workspace Architecture

As complexity grows, lib.rs is broken down into separate library crates inside a workspace (e.g., crates/banking_core, crates/db_store). Compilation can now occur in parallel across crates.

03
Multiple Binary Entry Points

Independent Micro-Binaries (src/bin/*)

The single lib.rs engine is shared across multiple binaries: a HTTP REST API Server (bin/api.rs), an Async Background Worker (bin/worker.rs), and an Admin CLI Tool (bin/cli.rs).

04
Distributed Microservices

RPC / Event-Driven Network Boundaries

The function calls originally defined in lib.rs translate into gRPC contracts or Kafka events. Struct validation rules (BankAccount::deposit) map directly to distributed domain-driven microservice guards.
